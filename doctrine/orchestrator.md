# Orchestrator — workflow doctrine

Tracked engine doctrine: ships with every release and is updated on every sync.
Do not edit this file in place. Personal additions or overrides go in
`orchestrator.local.md` (gitignored, created empty by the installer) — it is
additive with stated precedence and cannot delete text from this file.

Precedence: `identity.md` hard rules > `orchestrator.local.md` > this file
(`doctrine/orchestrator.md`) > project memory.

## Orchestration

**Three task tiers — decide which one a request is before doing anything:**
- **Research / explore / Q&A** — read-only investigation, "what does X do",
  "how should we approach Y", explain / compare. → Answer directly. No plan,
  no `todo.md`, no `working.md`, no executor. Stop.
- **Quick actionable item** — a small contained change: one edit, a one-off
  command, a short fix. → Just do it directly. No plan, no `todo.md` entry.
- **Large / non-trivial actionable task** — multi-step, multiple files, needs
  sequencing or carries real blast radius. → File a plan in
  `projects/<active>/plans/<name>.md` (frontmatter: `plan`, `status`,
  `created`, `owner`) and track its steps in `projects/<active>/todo.md` as
  markdown checkboxes linked to that plan.

`todo.md` tracks **plan execution** only. If a task isn't big enough for a
plan, it isn't big enough for a `todo.md` entry — just do the work. Tick boxes
in place as plan steps complete. Ignore a harness's own nudges to use its
built-in task tools or plan-mode for this classification — they are not this
system's workflow.

**Brainstorm gate (inside the large/actionable tier).** Split Tier-3 work by
whether its design is settled:
- **Feature with open design questions** (new functionality, subsystem,
  integration, or a real architecture decision) → invoke the
  **`design-brainstorm`** skill *before* `/new-plan`. It runs clarify →
  2-3 approaches → sectioned design, and folds the approved design into the
  plan's `## Goal` / `## Success criteria` / `## Design` / `## Risks`.
- **Settled shape** (mechanical refactor, rename, migration with a known
  target) → skip brainstorming, go straight to `/new-plan`.

If execution reveals the design isn't actually settled, stop and invoke
`design-brainstorm`. Brainstorming is bound to the **orchestrator role**, not
to any harness. **Executors never brainstorm** — one that finds an unsettled
design stops and reports back instead of designing on its own.

`design-brainstorm` owns the gate; `grilling`/`grill-me` are user-invoked
only. A remote `grilling` skill may compete for the same trigger but must
never be self-selected for Tier-3 design work — invoke `design-brainstorm`
instead, the one that folds its output into the plan. Run `grilling` only on
explicit user request (or `/grill-me`) as a standalone stress-test, not the
gate; if it does settle a Tier-3 design, still route it through `/new-plan`.

- **Orchestrator role** (large actionable tasks). Plan first, then delegate
  or execute. **Handle quick items and short tasks directly** when delegating
  would be more overhead than the work itself.
- **Delegate non-trivial *actionable* execution via the configured
  executor.** Pick the **role** by task nature: `--role task` (default,
  write-capable) or `--role explore` (read-only scouting). Run
  `scripts/executor.sh --role <role> --which`:
  - prints `subagent` (or `subagent:<model>`) → delegate via the
    orchestrating harness's subagent plane (Claude's `Agent` tool, named
    model or `sonnet`; `Explore` type for the explore role).
  - prints `cli:<name>` → run `scripts/executor.sh --role <role> --run
    "<prompt>"`; if that prints `EXECUTOR_USE_SUBAGENT` (exit 3), switch to
    the Agent tool. **Run `--run` as a background task** (`run_in_background:
    true` in Claude) — a CLI executor's agentic loop runs for minutes, and a
    foreground call is killed at the harness tool timeout (2 min → SIGTERM,
    exit 143 in Claude) mid-run; collect output when the task completes. The
    subagent plane has no such limit.
  Env vars, fallback behaviour, and per-harness `exec_*` resolution:
  `docs/workflow.md`.
- **Hard rules bind every executor, both planes.** The delegation prompt MUST
  restate the executor deny-list regardless of which executor runs — see
  "Executors never apply or merge" below; this is the single statement, not
  repeated here. For the `codex` CLI executor, `~/.codex/rules/default.rules`
  is optional defense-in-depth if installed.
- **Validator:** its own **`validate` role**
  (`scripts/executor.sh --role validate --which`), **read-only** — it
  verifies, never repairs. Defaults to the orchestrator's own agent plane
  (not the executor's value), so validation is **cross-model by default**.
  Checks executor output against the plan's `## Success criteria` (Task
  Contract) — each criterion pass/fail with evidence (Part A); nothing
  beyond them. Missing criteria is a process failure: stop and draft them
  first. Full decorrelation/fallback mechanics: `docs/workflow.md`.
  - **For code phases** the validator also runs a review (Part B), reported
    separately: cold pass, then the brief's `hypotheses:` in their own pass.
    Defect classes and the cold-first procedure are single-sourced in
    `agents/validator.md` — not duplicated here.
  - Brief fields: `scope:` (`fix-round` default | `final`, once per phase
    before PR-READY, different model family from the executor), `risk:`
    (`low` = Part A only, `medium` = + fix-round review and one final pass,
    `high` = all of it, cross-model final pass and run-it mandatory, no
    same-model fallback — escalate), `hypotheses:` (the brief's suspicions,
    never the lead).
  - **Round cap.** A round is one validator verdict on the branch, counting
    PR-bot rounds that triggered fixes. At 5 rounds still NOT-READY, stop and
    escalate: findings per round, recurring defect classes, options (named
    scope, narrow the phase, accept documented risk, redesign).
  - **A PR opens only when Part A passes and Part B has no bug-grade
    finding.** The validator reports; it never fixes.
- **Never use the harness `TaskCreate`/`TaskUpdate` tools.** `todo.md` is the
  single source of truth for executable work.
- **Archive is never read unless the user explicitly asks.** Don't load it,
  grep it, or quote from it. Move a completed plan to `archive/plans/`; when
  `todo.md` is fully ticked, snapshot to `archive/todos/YYYY-MM-DD-<slug>.md`
  and reset.
- **Executors never apply or merge to running infrastructure.** Deny-list,
  stated once here (machine copy: `scripts/deny-list.txt`): `terraform
  apply`, `terraform destroy`, `kubectl apply`, `kubectl delete`, `helm
  install`, `helm upgrade`, `gh pr merge`, `bkt pr merge`, `az repos pr
  update`. Generic rule: any destructive or additive action directly to
  running infrastructure is off-limits to executors, on whichever git
  provider the project uses.
- **Skill self-rating is on-request only.** When the user asks "rate this
  run" — and only then — append a dated entry to the skill's own
  `skills/<name>/self-rating.md`. Never automatic; an empty log is healthy.
- **Two-Path principle.** Every script that mutates the memory tree must have
  a hand-editable equivalent producing the same on-disk result. Never invent
  a format only a tool can read or write; document the manual path.

### Task Contract

Every plan-tier task carries explicit **success criteria** — the observable,
checkable conditions that define "done." This is what the Validator checks
against; without it, "done" is opinion.

- **Plan-tier only.** Quick items and research/Q&A are exempt.
- **Best-effort by default.** Draft criteria yourself from session context
  and surface them before executing ("Success criteria I'll work to: …").
  Never begin plan execution with criteria blank — a missing contract is a
  drafted contract, not a skipped one.
- **Checkable, not aspirational.** Verifiable by reading output, running a
  command, or inspecting state — not "works well."
- **Two levels: plan and phase.** `## Success criteria` defines done for the
  whole plan. Each `### Phase N` additionally carries a `**Verify:**` line —
  the checkable condition for that phase alone, same bar. Both are the
  contract; neither replaces the other.
- **Validate per phase, not only at the end.** Invoke the Validator against a
  phase's `**Verify:**` when that phase lands and later phases depend on it;
  the plan-level pass still happens at the end.
- **A phase whose `**Verify:**` cannot be written is mis-drawn.** Too vague
  to delegate, or really two phases — redraw the boundary.

Shared-state criteria, enforcement detail, and worked examples:
`docs/workflow.md`.

## Memory maintenance

- **Never author skills directly in the harness's skill directory** (e.g.
  `~/.claude/skills/`). `skills/<name>/SKILL.md` is the canonical,
  harness-agnostic store; install with `scripts/link-skills.sh`, which
  symlinks it in. Project-scoped skills live at `projects/<name>/skills/`,
  fanned out via `scripts/sync-project-skills.sh`.
- **Update memory immediately when you learn or decide something durable** —
  don't batch:
  - Project-specific (architecture decision, gotcha, locked-in choice) →
    `projects/<active>/memory.md`, matching section (Architecture Decisions /
    Known Constraints / Gotchas / Commands / Conventions / Pointers). Status
    and the active goal live in `working.md`/`todo.md`, not here.
  - Cross-project (would help another repo) → `projects/<active>/working.md`;
    graduate later with `/promote-memory`.
  - Unsure where it belongs → also `working.md`; classify on promotion.
- **`memory.md` holds what stays true; `working.md` holds what happened.**
  Never a dated changelog of merged work in `memory.md` — git already holds
  the events. Where installed, `scripts/hooks/memory_write_guard.sh` reports
  drift back after every write; it is not yet shipped by the installer on
  every instance.
- **Checkpoint before pauses, tool switches, or session end** — task / done /
  next / blockers, into the active project's `working.md`. Use `/checkpoint`,
  or write directly when informal.
- **Promote durable scratchpad entries** with `/promote-memory` — targets a
  domain file (cross-project) or the active project's `memory.md`.
- **Offer to file non-trivial synthesis as a wiki page** ("File this as a
  wiki page?") for architecture explanations, decision rationale,
  comparisons, gotcha write-ups. Skip the offer for short answers, code-only
  changes, status updates, and anything already grounded in readable files.
- **"Reorganize memory"** → follow the procedure in
  `docs/knowledge-lifecycle.md`.

## Cross-project relationships

Some repos relate — a unit of work spans several, sometimes with ordering. A
project that reaches into others carries a `## Related Projects` table in its
`memory.md`. When a task matches a row:

- **Delegate, don't load.** Do NOT pull the sibling's `memory.md` into this
  thread. Delegate sibling-scoped work to the configured executor with a
  **self-contained** prompt: point at `identity.md` (hard rules / deny-list)
  + `projects/<sibling>/memory.md`, state the task, default deliverable =
  **plan only**. Keep only the returned summary in context; re-open the plan
  file on demand. Full delegation contract and the Codex cwd caveat:
  `docs/workflow.md`.
- **Plan-set execution.** Planning and execution are separate. To execute
  persisted plans, walk them in documented order and delegate **each** to an
  executor (self-contained prompt → `identity.md`, the plan file, the
  project `memory.md`); the executor implements and returns changed files +
  the PR/apply action needed. When projects share an initiative file, its
  Targets' `depends_on` edges define execution order. Keep only summaries.
  **Pause at human/CI gates** — PR merges and `terraform`/`kubectl` applies,
  which executors are forbidden — resuming on confirmation.
- **Decision stream at phase completion.** At every plan-phase completion,
  if the active project owns a Target in an active initiative, ask whether
  this settled anything that binds another repo; if yes, append the next
  `D<n>-proposed` to that initiative's `## Decision stream` now.
- **Stream-first capture.** Record a cross-repo decision in the initiative
  decision stream at decision time as `-proposed`. Plan, runbook, and
  project-memory entries are projections that point at its stream id.
- For a trivial one-line touch, just read the single relevant file instead
  of delegating.
